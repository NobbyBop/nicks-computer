peanut: the tiny agent harness

i work with ai in my job, and we had recently spent a day doing a hackathon with the goal of building an agent harness that could solve a series of puzzles. it got me thinking, all the harnesses on the market are geared towards corporate models that you have to pay for. i don't like paying for ai (i seldom use it outside of work) so i thought i might try to build a small agent harness that would work on my laptop. something like claude code for local models (although not necessarily coding-focused).

to build this i ran local models on my laptop using ollama and wrote the harness in python.

version 1: a little chat program

the first version i came up with was a very basic chat experience. two features stand out to me as being somewhat notable.

  1. each chat is saved and summarized into a quick title. this could be useful if you had several conversations about different things. an example would be "finding lost car keys" or "explaining quantum mechanics." i ultimately cut this because it was unneeded for the low level of complexity that the conversations reached.

  2. tools are dynamically loaded and executed from auxillary python scripts

    from pathlib import Path import importlib import sys import os tools_path = os.environ.get("TOOLS_DIR") or "~/.peanut/.tools/" sys.path.insert(0, tools_path) def execute_tool(tool, *args): module_name = tool module = importlib.import_module(module_name) module.__getattribute__(tool)(*args) def resolve_tools(): importlib.invalidate_caches() module_names = os.listdir(tools_path) module_names = list(filter(lambda x: ".py" in x, module_names)) module_names = list(map(lambda x: x.strip(".py"), module_names)) tools = {} for module_name in module_names: module = importlib.import_module(module_name) tools[module_name]=module.__getattribute__(module_name) return tools

    this is interesting because it theoretically allows tools to be generated mid-session by peanut itself. it just needs to write a tool to the correct location in the expected format. each turn the loop re-loads the tools. however, as i will show later, this didn't work very well for local models, i suspect the openai api is too token-heavy for small models in how it passes tool information to the model.

version 2: clever but overkill

i noticed a big problem when running this version of peanut. following the documented ollama and openai patterns was confusing the model on whose turn it was to speak, which was manifesting as a lack of responses after tool calls, or tools in a loop.

my first attempt to fix this was to intercept the conversation and build a custom prompt each time. it went something like this:

  1. take the conversation so far, have an llm choose the relevant entries to whatever the most recent message was

  2. take those selected messages, have another llm summarize them into useful context

  3. give only the most recent message and context summary to peanut

as an idea, it wasn't so bad. in practice, it worked most of the time but it didn't help with context enough to make much of a difference, and it introduced more room for error by giving more work to llms

version 3: simpler is better

when developing peanut i lost sight of what the actual goal was: a tiny but useful agent you could run on your computer. so for this next (and final) version, i took what i had learned and built peanut into a conversational agent that can run commands on your terminal.

the main changes were stripping out sessions and pivoting away from the built-in tool schema to a custom-defined json response shape that i could parse myself

class Action(Enum): respond = "respond" execute = "command" class ResponseFormat(BaseModel): action: Action message: str | None command: str | None

the model almost always chooses the correct option between these, which was a big improvement! the only issue is it really struggles with powershell commands. i think in terms of usability it is still a bit too clunky to actually help you in your terminal. however, in terms of tool calling, this is absolutely the way to go for small local models.

as i mentioned i don't really use ai outside of work, so i'm satisfied with the learnings of making this project, even though its utility is questionable.

an ideal final version would be closer to version 1 (which i have on the legacy branch of the repo), but adding specific tools as i need them (feel free to do this for me if you want to because peanut is on github).
